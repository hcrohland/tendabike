# SvelteKit SPA mode served by an external Rust axum binary (`ServeDir`)

**Origin.** Research ticket #725 — the canonical setup for an SPA-mode SvelteKit app
(`ssr: false`) that is built to static files and served by an **external** server (our
Rust axum binary via `tower_http::services::ServeDir`), not by SvelteKit's own
dev/preview server. Findings verified against primary sources (official SvelteKit docs,
the `@sveltejs/adapter-static` source, and the `tower-http` API docs) as of 2026-11-04.

**Question.** How does an SPA-mode SvelteKit app (`ssr: false`) built to static files and
served by an external axum binary via `ServeDir` work end to end? Specifically:

1. Which adapter, and the exact SPA config — where does `ssr: false` live, and what is the
   adapter's `fallback` option.
2. What the build output looks like (directory, files, the fallback page).
3. How deep links / full-page refreshes on client routes (e.g. `/part/5`) are served —
   exactly what the external server must do, and whether `ServeDir` can do it or the axum
   app needs an explicit fallback route.
4. How the dev server proxies to the backend — does SvelteKit honor the existing
   `server.proxy` in `vite.config.ts`?
5. How the existing Vite plugins (`paraglideVitePlugin`, `tailwindcss()`, vitest) coexist
   with the `sveltekit()` plugin.

**Bottom line.** Use `@sveltejs/adapter-static` with `fallback: '200.html'`, set
`export const ssr = false` in the **root `+layout.ts`** (a SvelteKit *page option*, not a
`vite`/`svelte.config` setting), and configure the adapter **inside `sveltekit({ adapter: … })`
in `vite.config.ts`**. The single most important implication for the migration: **`ServeDir`
has no implicit SPA fallback — by default it returns `404` for any path that is not a real
file — so the axum app must chain `.fallback(ServeFile::new(<dist>/200.html))` onto the
`ServeDir`.** Use `.fallback()` (which returns the fallback service's status, i.e. `200`),
not `.not_found_service()` (which forces `404`). The dev proxy and the existing Vite plugins
carry over unchanged; the only plugin change is dropping the standalone `svelte()` plugin in
favour of `sveltekit()`.

## 1. Adapter + exact SPA config

**Adapter:** `@sveltejs/adapter-static`. It is the only adapter that produces a purely
static output (no server at runtime), which is what an external `ServeDir` needs.
SvelteKit's SPA docs state it is the adapter to use when the app has *no server-side
logic* (no `+page.server.js` / `+layout.server.js` / `+server.js`):

> "If you don't have any server-side logic (i.e. `+page.server.js`,
> `+layout.server.js` or `+server.js` files) you can use `adapter-static` to create your SPA."
> — <https://svelte.dev/docs/kit/single-page-apps>

**Where `ssr: false` lives — the root `+layout.ts`, not `svelte.config.js`.** `ssr` is a
SvelteKit **page option**, declared as a module-level export in a `+layout` / `+page` file.
Setting it in the *root* layout disables SSR app-wide, which is exactly what turns the app
into an SPA:

> "If you add `export const ssr = false` to your root `+layout.js`, your entire app will
> only be rendered on the client — which essentially means you turn your app into an SPA.
> You should not do this if your goal is to build a statically generated site."
> — <https://svelte.dev/docs/kit/page-options> (§ `ssr`) and
> <https://svelte.dev/docs/kit/single-page-apps> (§ Usage)

```ts
// src/routes/+layout.ts
export const ssr = false;
```

`ssr` does **not** belong in `svelte.config.js` (that file is Svelte *compiler* config —
preprocess, kit plugin options) and not in `vite.config.ts`. It is a per-route page option,
and for SPA mode it is set once, in the root layout. So for us: **one line in
`src/routes/+layout.ts`**, and `svelte.config.js` stays as-is (see §5).

**The adapter's `fallback` option.** `fallback` names the HTML page SvelteKit generates as
the SPA entry point — served for any URL that is not a static asset or a prerendered page.
The docs recommend **avoiding `index.html`** (it can collide with a prerendered homepage);
`200.html` is the conventional name:

> "To create a single page app (SPA) you must specify the name of the fallback page to be
> generated by SvelteKit, which is used as the entry point for URLs that have not been
> prerendered. This is commonly `200.html`, but can vary depending on your deployment
> platform. You should avoid `index.html` where possible to avoid conflicting with a
> prerendered homepage."
> — <https://svelte.dev/docs/kit/adapter-static> (§ `fallback`)

The adapter is configured **inside the `sveltekit()` Vite plugin in `vite.config.ts`**, not
in `svelte.config.js`:

```ts
// vite.config.ts
import adapter from '@sveltejs/adapter-static';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
	plugins: [
		sveltekit({
			adapter: adapter({
				fallback: '200.html' // may differ from host to host
			})
		})
	]
});
```
> — <https://svelte.dev/docs/kit/single-page-apps> (§ Usage)

**Summary of the three settings and where each lives:**

| Setting | Value | Lives in |
| --- | --- | --- |
| `ssr` | `false` | `src/routes/+layout.ts` (page option) |
| adapter | `@sveltejs/adapter-static` | `vite.config.ts` → `sveltekit({ adapter })` |
| `fallback` | `'200.html'` | `vite.config.ts` → `adapter({ fallback })` |

## 2. Build output

**Output directory defaults to `build/`** — both `pages` and `assets` default to the string
`'build'`. This is set by the adapter options, read in `adapt()` in the adapter source:

```js
const { pages = 'build', assets = pages, fallback, precompress } =
	options ?? platform?.defaults ?? {};
rmSync(assets, { force: true, recursive: true });
rmSync(pages,   { force: true, recursive: true });
builder.generateEnvModule();
builder.writeClient(assets);      // client JS/CSS + contents of static/
builder.writePrerendered(pages);  // prerendered .html pages (none, when ssr=false)
if (fallback) {
	await builder.generateFallback(path.join(pages, fallback)); // -> <pages>/200.html
}
```
> — <https://github.com/sveltejs/kit/blob/main/packages/adapter-static/index.js> and
> <https://svelte.dev/docs/kit/adapter-static> (§ `pages`, § `assets`)

`assets` "should be the same as `pages` … it will default to whatever the value of `pages`
is" — so setting `pages` alone redirects both.
> — <https://svelte.dev/docs/kit/adapter-static> (§ `assets`)

**What a pure-SPA build (`ssr = false` globally) produces.** Because no page is prerendered
when SSR is off app-wide, `writePrerendered` emits nothing and the output is:

```
dist/
  200.html            # the fallback page (generated from src/app.html)
  _app/
    version.n.json    # build manifest
    assets/           # hashed client JS + CSS (e.g. entry-*.js, start-*.css)
  <static files>      # copied verbatim from frontend/public/ (favicon, css, …)
```

There is **no `dist/index.html`** in a pure-SPA build — only `200.html`. (If you later opt
individual pages into prerendering, those land under `dist/<route>/index.html`, which is
precisely why the docs steer the fallback away from `index.html`.)

**The fallback page** "is an HTML page created by SvelteKit from your page template
(e.g. `app.html`) that loads your app and navigates to the correct route", and it
"will always contain absolute asset paths (i.e. beginning with `/` …) since it is used to
respond to requests for arbitrary paths".
> — <https://svelte.dev/docs/kit/single-page-apps> (§ Usage)

> **Consequence for us:** our `Dockerfile` copies `frontend/dist` and sets
> `STATIC_WWW="/tendabike/dist"`, so we set `pages: 'dist'` in the adapter options to keep
> SvelteKit's output directory aligned with the existing container layout (no Dockerfile
> change needed). See the Recommended setup.

## 3. Deep links / full-page refreshes (the crux)

**What the external server must do:** for any request path that is *not* a real file in
`dist/` and *not* an API route (`/api`, `/strava`), serve the fallback page (`200.html`)
with a `200` status. The browser loads the SPA shell, which then client-side-routes to the
requested path (e.g. `/part/5`). This is the same "serve `200.html` for client-side
routing" pattern the SvelteKit SPA docs show for Surge and for Apache
(`RewriteRule . /200.html [L]` when the file isn't found):
> — <https://svelte.dev/docs/kit/single-page-apps> (§ Usage, § Apache)

**Does `ServeDir` support a file fallback? Yes — via `.fallback()` / `.not_found_service()`.**
The `tower-http` `ServeDir` API is explicit about this. By default, `ServeDir` returns
`404 Not Found` when the file does not exist; both methods let you replace that behaviour:

> **`fallback`** — "Set the fallback service. This service will be called if there is no
> file at the path of the request. **The status code returned by the fallback will not be
> altered.**"
> Example: `ServeDir::new("assets").fallback(ServeFile::new("assets/not_found.html"))`
>
> **`not_found_service`** — "Set the fallback service and **override the fallback's status
> code to `404 Not Found`**." … "Setups like this are often found in single page
> applications."
> — <https://docs.rs/tower-http/latest/tower_http/services/struct.ServeDir.html>
> (methods `fallback`, `not_found_service`; default 404 behaviour in the struct docs)

So the axum app does **not** need a separate explicit fallback *route*. It chains the
fallback onto the existing `ServeDir`. The current line:

```rust
// backend/axum/src/lib.rs (today)
let app = routes(app_state)
    .fallback_service(tower_http::services::ServeDir::new(path))
    …;
```

becomes:

```rust
use tower_http::services::{ServeDir, ServeFile};

// `path` is the canonicalised STATIC_WWW dir (…/dist)
let app = routes(app_state)
    .fallback_service(
        ServeDir::new(path.clone())
            .fallback(ServeFile::new(path.join("200.html"))),
    )
    …;
```

**Use `.fallback()`, not `.not_found_service()`.** The distinction is the response status:
- `.fallback(ServeFile::new(…))` → the `ServeFile`'s own status is used → **`200`**. This is
  what a SPA wants: a `200` with the app shell so the client router can take over.
- `.not_found_service(ServeFile::new(…))` → status forced to **`404`** (body is still the
  shell). Semantically wrong for a valid client route and can confuse tooling/clients that
  branch on status.

Both still serve the `200.html` body; only the status differs. For SPA deep links we want
`200`, hence `.fallback()`.

**Routing precedence is already correct in our app.** `routes()` nests `/api` and `/strava`
first; `fallback_service` is only consulted for paths that match no route. So a deep link
like `/part/5` (not a route, not a file) hits `ServeDir` → no file → `.fallback` →
`200.html` (`200`). A request for a real asset like `/app/assets/entry-xyz.js` is served
directly by `ServeDir`. A request to `/api/parts` is handled by the API router and never
reaches `ServeDir`.

**Minor caveats (both fine with defaults):**
- `call_fallback_on_method_not_allowed` defaults to `false` — non-`GET`/`HEAD` requests that
  miss a file get `405`, not the fallback. We only need `GET` for full-page refreshes, and
  mutations go to `/api`, so the default is correct.
- Since `0.7.0`, a *file* path with a trailing slash (e.g. `/part/5/` when `5` is a file)
  returns `404`; that then routes to the fallback, which is acceptable. Our client routes
  are directory-style, so this is a non-issue.
  — <https://github.com/tower-rs/tower-http/blob/main/tower-http/CHANGELOG.md> (0.7.0)

## 4. Dev server proxy to the backend

**SvelteKit's dev server *is* Vite's dev server, and it honours `server.proxy` as-is.**
SvelteKit is "really just a Vite project that uses the `@sveltejs/kit/vite` plugin, along
with any other Vite configuration", so the `server` block in `vite.config.ts` (including
`server.proxy`) is passed straight through to Vite's dev server:
> — <https://svelte.dev/docs/kit/project-structure> (§ `vite.config.js`)

SvelteKit's FAQ points at Vite's proxy as the recommended local-dev mechanism for an
external backend, confirming no SvelteKit-specific mechanism is needed:

> "If you wish to use this method, you may find `handleFetch` helpful. … Another approach
> is to set up a proxy to bypass CORS headaches. In production, you would rewrite a path
> like `/api` to the API server; **for local development, use Vite's `server.proxy`
> option**."
> — <https://svelte.dev/docs/kit/faq> (§ "How do I use a different backend API server?")
> (links Vite's `server.proxy`: <https://vitejs.dev/config/server-options.html#server-proxy>)

So the existing block carries over unchanged:

```ts
// vite.config.ts — unchanged by the migration
server: {
  host: "127.0.0.1",
  proxy: {
    "^/(api)|(strava)": {
      target: "http://localhost:8000",
      changeOrigin: true,
    },
  },
},
```

Vite's proxy keys may be a string (prefix) **or a `RegExp`**; a `RegExp` key is tested
against the request path. A couple of notes on our specific key `^/(api)|(strava)`:

- It matches `/api/…` (anchored `^/(api)`) and any path containing `strava` — the
  `(strava)` alternative is *unanchored* (the `^/` binds only to the first alternative), so
  `/strava/…` matches via the substring. For our routes this behaves correctly:
  `/part/5` matches neither branch → not proxied → served by the SvelteKit dev server
  (the SPA route). That is exactly the behaviour we want.
- This is a pre-existing config detail, not something the migration changes; the only
  requirement is that it keeps working, which it does because SvelteKit defers to Vite.

**Production note (for contrast):** in production there is no Vite proxy — the single axum
binary serves both `/api`/`/strava` (real handlers) and the static SPA (fallback). So the
`server.proxy` is purely a dev-time concern and needs no production counterpart.

## 5. Coexisting Vite plugins

**SvelteKit is a Vite plugin; `sveltekit()` sits in the `plugins` array alongside the
others.** "A SvelteKit project is really just a Vite project that uses the
`@sveltejs/kit/vite` plugin, along with any other Vite configuration. The plugin accepts
your Svelte and SvelteKit configuration."
> — <https://svelte.dev/docs/kit/project-structure> (§ `vite.config.js`)

The key changes to the plugin list when moving off plain Vite:

- **Drop the standalone `svelte()` plugin** (`@sveltejs/vite-plugin-svelte`). `sveltekit()`
  performs Svelte compilation itself and reads `svelte.config.js` for the compiler options
  (including `preprocess`). Keeping `svelte()` alongside `sveltekit()` would double-process
  Svelte files.
- **Keep `svelte.config.js` as-is** — `preprocess: vitePreprocess()` is read by SvelteKit.
  (The `vitePreprocess` import comes from `@sveltejs/vite-plugin-svelte`, which SvelteKit
  depends on, so it remains available.)
- **Keep `paraglideVitePlugin(…)` and `tailwindcss()`** — they are ordinary Vite plugins and
  coexist with `sveltekit()`.
- **Keep the vitest `test` block.** Importing `defineConfig` from `vitest/config` (as we do
  now) is the recommended way to get both the `test` block and Vite config typing.
- **Plugin order:** `sveltekit()` should generally be **last**. SvelteKit's own docs show
  ecosystem plugins that "must come before the SvelteKit plugin" (e.g.
  `@sveltejs/enhanced-img`), and show custom `configureServer` middleware plugins listed
  before `sveltekit()`. Ordering `paraglide` and `tailwind` before `sveltekit()` is the safe
  arrangement.
  > — <https://svelte.dev/docs/kit/images> (§ `@sveltejs/enhanced-img` Setup),
  > <https://svelte.dev/docs/kit/faq> (§ "How do I use middleware?")

**Resulting `vite.config.ts` shape** (plugins + the parts we already have):

```ts
import adapter from "@sveltejs/adapter-static";
import { paraglideVitePlugin } from "@inlang/paraglide-js";
import tailwindcss from "@tailwindcss/vite";
import { sveltekit } from "@sveltejs/kit/vite";
import { defineConfig } from "vitest/config";

export default defineConfig({
  plugins: [
    paraglideVitePlugin({
      project: "./project.inlang",
      outdir: "./paraglide",
      strategy: ["cookie", "preferredLanguage", "baseLocale"],
    }),
    tailwindcss(),
    sveltekit({
      adapter: adapter({
        pages: "dist",      // match the Dockerfile's dist/ + STATIC_WWW
        assets: "dist",     // (defaults to pages; shown for clarity)
        fallback: "200.html",
      }),
    }),
  ],

  resolve: { conditions: ["browser"] },   // unchanged

  test: { /* unchanged vitest config */ },

  build: { /* unchanged */ },

  server: {
    host: "127.0.0.1",
    proxy: {
      "^/(api)|(strava)": { target: "http://localhost:8000", changeOrigin: true },
    },
  },
});
```

## Recommended setup for tendabike

Tying the findings to our concrete setup (Svelte 5 app, axum `ServeDir` fallback,
`Dockerfile` → `dist/`, currently hash-routed via `svelte-spa-router`):

1. **Dependencies.** Add `@sveltejs/kit` and `@sveltejs/adapter-static`. Remove
   `svelte-spa-router` (replaced by SvelteKit's file-based routing). Keep
   `@sveltejs/vite-plugin-svelte` only for the `vitePreprocess` import in
   `svelte.config.js` (SvelteKit depends on it anyway).

2. **`svelte.config.js` — unchanged:** `export default { preprocess: vitePreprocess() };`

3. **`vite.config.ts`** — as in §5: replace `svelte()` with
   `sveltekit({ adapter: adapter({ pages: "dist", assets: "dist", fallback: "200.html" }) })`;
   keep `paraglideVitePlugin`, `tailwindcss()`, the vitest `test` block, `resolve.conditions`,
   and `server.proxy`. Setting `pages: "dist"` keeps SvelteKit's output aligned with the
   existing `Dockerfile` (`COPY …/frontend/dist dist`) and `STATIC_WWW="/tendabike/dist"`, so
   **no Dockerfile change is needed.**

4. **App template.** Convert `frontend/index.html` → `src/app.html` using SvelteKit's
   template tags: replace the manual `<div id="app"></div>` + `<script … src="/src/main.ts">`
   with `%sveltekit.head%` / `%sveltekit.body%`; keep the `<head>` metadata (title, favicon,
   plotly script). The adapter generates `dist/200.html` from this template. Delete
   `frontend/index.html`.

5. **Routing.** Replace `src/App.svelte` (the `svelte-spa-router` table) and `src/main.ts`
   (the `new App().mount(…)` entry) with SvelteKit file-based routes under `src/routes/`
   (e.g. `src/routes/+page.svelte`, `src/routes/part/[id]/+page.svelte`, …). Add
   `src/routes/+layout.ts` containing `export const ssr = false;` — this is the single switch
   that puts the app in SPA mode.

6. **axum fallback (the load-bearing change).** In `backend/axum/src/lib.rs`, change
   `.fallback_service(ServeDir::new(path))` to
   `.fallback_service(ServeDir::new(path).fallback(ServeFile::new(path.join("200.html"))))`.
   Use `.fallback()` (→ `200`), **not** `.not_found_service()` (→ `404`). No new axum route
   is required; `ServeDir` handles the "serve the SPA shell for any missing file" behaviour
   internally, and `/api` + `/strava` keep taking precedence via the router.

7. **Dev.** No change to `server.proxy` — SvelteKit's dev server (Vite) honours it, so
   `/api` and `/strava` still proxy to `http://localhost:8000` while everything else is served
   by the SPA.

**The single most important implication:** `tower_http::services::ServeDir` has **no
implicit SPA fallback** — by default it returns `404 Not Found` for any path that is not a
real file, so deep links like `/part/5` would 404 on a full-page refresh. The axum app must
explicitly attach a file fallback
(`ServeDir::new(path).fallback(ServeFile::new(path.join("200.html")))`, returning `200`) —
and the SvelteKit `fallback` must be named `200.html` (not `index.html`) so the file it serves
exists in `dist/` and does not collide with a future prerendered homepage.
