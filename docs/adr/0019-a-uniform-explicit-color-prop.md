# ADR-0019: A uniform explicit color prop

## Status

Accepted. The app's neutral color is one uniform `color` prop (`"primary"` or `"secondary"`) that the caller writes explicitly on the neutral *surfaces* — cards and the Tone block — with no context and no hidden state. Chips and neutral buttons take no color: they all render a single uniform fill. The theme defines the complete neutral style as role classes: a **surface** role per color (background + text + border) and a **single fill** role (one tone, background + text — dark in light mode, white in dark mode), plus a muted-text class and a page-base text color. This supersedes the surface/tone flip half of [ADR-0017](archive/0017-a-gray-first-two-tone-color-scheme.md) (now in [`archive/`](archive/)). ADR-0017's other accepted decisions stand and are recorded here: the gray-first two-tone palette (primary light, secondary darker) and the vivid status-hue mapping (danger=red, warning/due-soon=yellow, success=green, info/unread=blue).

## Context

ADR-0017 settled the app's color scheme: a single unified, gray-first scheme defined once in the theme (`frontend/src/app.css` `@theme`) — two neutral gray tones, `primary` (light) and `secondary` (darker), with status colors on the standard (vivid) Tailwind hue scales. It also decided the *mechanism* for card/content contrast: a context-based surface/tone flip. A `Card` picked one of the two tones and published it to its children through a context; a nested `Card` flipped to the opposite tone, and content (text, buttons) contrasted the card by reading the published tone and taking the opposite. That mechanism lived in a dedicated module of hand-rolled class-string helpers (`frontend/src/Widgets/tone.ts`: `Tone`, `bg()`, `border()`, `mainText()`, `mutedText()`, `opposite()`, `currentTone()`, `contrastBg()`).

The flip worked, but it was built the wrong way for Tailwind: a component's color depended on invisible ancestor state, so it was hard to follow and not how the component library is meant to be used. The implementation pass therefore retired the flip in favor of a uniform `color` prop — but it left the actual styles in a dedicated TypeScript module of hand-rolled class strings (`frontend/src/Widgets/color.ts`): a color mapped to its surface classes, plus shared fill and text constants. A component's complete style was therefore assembled in application code, not defined by the theme — the theme only defined the raw color scales.

Rendering the result in a real browser also showed that the per-color fill the original spec called for does not work: each tone's own fill step reads too dark on the light surface in light mode and too light on the dark surface in dark mode, and the two different fills make chips and buttons inconsistent with each other. The rendered fix is a **single uniform fill** — one value, stable between the primary and secondary card surfaces — that every chip and neutral button renders.

The goal is for the theme itself to define what each role means — a surface per color (background, text, border) and the single uniform fill (background, text) — so that a neutral card or Tone block that carries `color="primary"` (or `"secondary"`) gets its surface from the theme automatically, and a chip or neutral button gets the uniform fill from the theme automatically. No mapping module, no class-string assembly, no hand-rolled strings.

## Decision

**One uniform `color` prop — `"primary"` (the light tone) or `"secondary"` (the darker tone) — on every neutral surface, written explicitly by the caller. There is no context, no flip, and no hidden state: a surface's color depends only on the prop on it.** The same color value means the same thing on every surface; the contrast comes from two places: the surface's *color within the same scale* (a `primary` surface reads the light step, a `secondary` surface the darker one) and the *fill sitting between the two surfaces* (the same value on either surface, so every chip and button is visible and identical wherever it appears). The theme's two gray scales are already shaped to make this work; no color values change.

**The theme owns the complete neutral style.** The theme CSS defines, for each of the two neutral colors, a *surface* role class (background + text + border), plus a *single fill* role class (one tone, background + text — dark in light mode, white in dark mode), a muted-text class, and a page-base text color in the base layer. Each class is built from the existing scale values with a light-mode step and a dark-mode step, so the same class reads correctly in both modes. No scale values are added, removed, or edited.

- **Cards and the Tone block render a surface** — the theme's surface role class of their color, applied via the framework's class directive (the literal class names are written out, never interpolated, so the CSS framework scans them). A top-level card defaults to `secondary`.
- **Chips and neutral buttons render the single uniform fill** — the theme's one fill role class: `primary-200` in light mode with dark text, and `secondary-700` in dark mode with white text. The fill does not vary by the card's color; both steps were chosen to stay legible on the lighter (secondary) card surface in their mode.
- **Only surfaces carry a color.** A card and the Tone block take a `color` (their surface). The chips and buttons inside them do not — they render the uniform fill, so there is no per-widget color to match.
- **Only nested cards flip.** A card (or Tone block) inside a card takes the opposite color, authored explicitly by the caller. There is no context, no inheritance of the color value, and no automatic flip.
- **Text is inherited, not repeated.** The surface role class sets the text color, so text inside a neutral surface inherits it; the shared main-text constant is deleted from all its call sites. Page-base text (outside any surface) gets the main color from the theme's base layer, which sets the text color only — no page-base background. Status, muted, and white-on-fill text set their own color and override the inheritance.
- **Muted text is a theme class.** Muted (caption) text uses the theme's muted-text class in both modes, replacing the shared muted-text constant at its call sites.
- **Neutral buttons render the fill role, like chips.** A neutral button is a plain button element carrying the theme's fill class, wrapped in one shared neutral button widget used by the dialog footers, the "show more" action, and the close action. The component library's button is retained only for status colors (e.g. destructive red), because it composes its color classes from a hard-coded internal table by plain concatenation and a theme class cannot override them (verified cascade behavior of the CSS framework version in use).
- **Exceptional layouts compose standard utilities at the call site.** Call sites that need a background without a border (or any other partial style) write standard utilities directly; the theme defines no background-only variant.

**The shared TypeScript class mapping is deleted.** The module that mapped a color to its surface class strings and carried the shared fill and text constants goes away; the `Color` type survives as a type-only module so the prop plumbing between the surface components keeps working. The tone module and the boolean `light` prop (retired by the implementation pass) are gone, and the codebase has exactly one way to do neutral color.

**Standing from ADR-0017.** The gray-first two-tone palette — `primary` (the light tone) and `secondary` (the darker tone), each defined once in the theme with a light-mode step and a dark-mode step, so the same class reads correctly in both modes — and the vivid status-hue mapping: danger (overdue/alert, errors, destructive actions, not-found) = red; warning (due-soon) = yellow; success (ok/healthy, approve/confirm) = green; info (unread, primary call-to-action) = blue; neutral (empty states, dismiss) = the darker tone. Provider brand colors (Strava, intervals.icu) remain inline, outside the theme.

## Rejected alternatives

- **A shared TypeScript color→classes mapping.** (The implementation pass's mechanism: the theme defines the scales, and a small module maps a color to its surface class strings and carries the shared fill and text constants.) Rejected: it is plain data that carries no state, but it leaves the style recipe — which tokens form a surface — in application code. A component's complete style is assembled in TypeScript, not defined by the theme.
- **Theme tokens only.** Define the scales in the theme and let application code compose the role classes from tokens. Rejected: tokens are values, not groupings — the recipe stays in application code, and because the CSS framework cannot generate classes from interpolated names (`surface-${color}` is never scanned), a color → full-class-string lookup reappears in TypeScript: the mapping module by another name.
- **The context-based surface/tone flip.** (ADR-0017's mechanism.) Rejected: a component's color depended on invisible ancestor state, so it was hard to follow and not how the component library is meant to be used. The library already expects `primary` and `secondary` to be ordinary color scales that each component reads for its own background, text, and border.
- **Per-color fills (each tone its own fill step, chip/button matching its card).** This was the original fill decision of this ADR: `primary` a darker fill, `secondary` a lighter one. Rejected after rendering in the browser: the per-color fills read too dark on the light surface in light mode and too light on the dark surface in dark mode, and the two different fills made chips and buttons inconsistent with each other. A single uniform fill, sitting between the two card surfaces, reads cleaner in both modes and keeps every chip and button visually identical.

## Consequences

- The theme CSS is the single source of the app's neutral color: a surface role class per color, the single uniform fill, the muted-text class, and the page-base text color. `frontend/src/Widgets/color.ts` is a type-only module (the `Color` prop's type); the tone module and the class mapping are gone; the codebase has exactly one way to do neutral color.
- A surface's color is visible at its call site — there is no ancestor state to reason about, and a nested card's flip is readable in the code (the caller writes the opposite color).
- The look shifts in two intended ways: neutral buttons become gray filled (instead of white-on-card), and chips become filled, button-like elements (instead of light surfaces). Both render the same uniform fill, so chips and buttons are visually consistent with each other across the app.
- The theme's color values are unchanged: the surfaces and the fill read existing steps (`primary-200` light / `secondary-700` dark for the fill); status colors and provider brand colors are untouched.
- Text inside a neutral surface inherits the surface's text color; the shared main-text constant is gone from all its call sites, and muted (caption) text uses the theme's muted-text class.
- Tests assert the rendered role class of the card, the Tone block, the chip, and the neutral button — never the mechanism, which no longer exists. A rendered color is not inferable from theme tokens, so the rendered colors are verified in a real browser via the component-verification harness (computed styles in both light and dark mode).
- The frontend coding-standards doc (`frontend/AGENTS.md`) records the theme-role-class convention — surface per color vs the single fill, text inheritance, the button convention, and "only surfaces carry a color, only nested cards flip" — replacing the two-tone flip description.
